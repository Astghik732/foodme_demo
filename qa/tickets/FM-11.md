## Description

The pricing and delivery-fee calculation (line totals, subtotal, delivery
fee, free-delivery threshold) has no dedicated automated test coverage. The
only checks are incidental, exercised as a side effect of the general
order-creation happy-path test. Several customer reports about totals looking
wrong (see FM-1, FM-2) had to be investigated manually because there was no
existing test isolating the calculation logic to compare against.

## Steps to reproduce

N/A — process/coverage gap, not a runtime defect.

## Expected vs actual

**Expected:** pricing logic (line total rounding, subtotal sum, delivery fee
selection, free-delivery threshold comparison) has unit tests covering
typical values, boundary values (subtotal exactly at the free-delivery
threshold), and multi-line orders.

**Actual:** no such tests exist; regressions in pricing logic are only caught
if someone happens to notice the resulting number looks wrong.

## Acceptance criteria

- Unit tests exist for the delivery-price calculation covering: below
  threshold, exactly at threshold, and above threshold, for both `DELIVERY`
  and `TAKEAWAY`.
- Unit tests exist for order total calculation covering single-line and
  multi-line orders with varied quantities.
- Tests are wired into the existing backend test suite (`./gradlew test`) and
  into CI.

## Environment

Backend (`apps/backend`), JUnit.
