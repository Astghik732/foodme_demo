## Description

Error responses aren't consistent across the public API and the admin API.
Some endpoints return the standard Spring error body (`timestamp`, `status`,
`error`, `message`, `path`), while others return an ad hoc `{"message": "..."}`
shape, and at least one observed 500 response included a full stack trace in
the body instead of a generic message. This makes writing robust error
handling in both frontends harder than it should be, and is inconsistent with
what's documented in `docs/api-contract.md`.

## Steps to reproduce

1. Trigger a validation error on `POST /api/order` (e.g. an unsupported
   `paymentType`) and note the response shape.
2. Trigger a not-found error on `GET /api/chef/{id}` with a nonexistent id
   and note the response shape.
3. Trigger an unexpected server error (e.g. malformed input that isn't
   validated) and note what the response body contains.
4. Compare the three shapes.

## Expected vs actual

**Expected:** every error response follows the single shape documented in
`docs/api-contract.md`, regardless of which endpoint or error type produced
it, and never includes internal details like a stack trace.

**Actual:** response shapes vary by endpoint and error type, and at least one
error path leaks internal implementation detail in the response body.

## Acceptance criteria

- A single global exception-handling mechanism produces the documented error
  shape for every `/api/**` and `/admin/**` error response.
- No response body includes a stack trace or other internal detail, in any
  environment.
- Existing and new tests assert on the error shape for at least one
  validation error, one not-found error, and one unexpected-error case.

## Environment

Backend (`apps/backend`), all environments — the stack-trace leak was
observed on the demo/staging environment and should be checked against
production configuration as part of the fix.
